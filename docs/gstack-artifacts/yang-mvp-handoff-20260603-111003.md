## 1. Build Target

What this build produces in one sentence:

> A playable one-screen Battle Lab where target players can watch `Launch / Tuning / Unit` machine events turn into three distinct frontline pressure patterns, then answer blind causality questions after each battle.

Hypothesis:

> Target players can distinguish `Launch Flood`, `Tuning Echo`, and `Unit Queue Burst` as different machine-to-frontline patterns, and `Unit` does not become the only axis they can explain, trust, or prefer.

Soul:

> The machine-to-frontline causal trace. If the player cannot see a machine-axis event happen before the matching frontline change, this is not the same mechanic.

Build time target:

- 3-7 development days after choosing a simple runtime.
- Add 1-3 days if a fresh project scaffold is needed.

## 3. Gameplay Requirements (what the PLAYER must experience)

| Player Action | Expected Response | Timing | Feel Target |
|---|---|---|---|
| Start `Launch Flood` battle | Player sees Pool rhythm, return arrows, and repeated small launches before the frontline becomes a sustained flow. | First clear Launch trace within first 10 seconds. Counter warning once during the 60-90 second battle. | Player reads "the machine is feeding pressure continuously", not just "more units appeared." |
| Start `Tuning Echo` battle | Player sees `Prime / Echo / Surge` slots, an Echo hot-slot window, copy afterimages, then fewer but larger repeated frontline hits. | First Echo copy read within first 15 seconds. Counter warning before a copy is weakened or swallowed. | Player reads "the same hit counted again" before the frontline jump. |
| Start `Unit Queue Burst` battle | Player sees Unit slot chunks fill, same-unit queue entries stack, a squad bracket form, then a quiet gap followed by one grouped push. | First queue buildup visible within first 15 seconds. First batch release before mid-battle. | Player reads "a batch charged up, then released", not "a faster stream." |
| Use `Launch Overdrive` | Button is attached to Launch lane and pulses only when return balls, Pool pressure, or launcher throughput can be amplified. Activation intensifies return arrows and launcher cadence. | Click response within 100ms. Visible axis amplification starts within 250ms. | Player reads `Overdrive` as Launch amplification, not rescue. |
| Use `Tuning Overdrive` | Button is attached to Tuning lane and pulses only when Echo hot state or Echo window exists. Activation makes Echo afterimages persist or repeat without consuming hot state. | Click response within 100ms. Copy feedback starts on the next relevant hit. | Player reads `Overdrive` as Echo repetition amplification. |
| Use `Unit Overdrive` | Button is attached to Unit lane and pulses only when squad chain or same-unit queue buildup exists. Activation releases or extends the squad chain. | Click response within 100ms. Squad bracket response within 250ms or on the next queue beat. | Player reads `Overdrive` as squad-chain amplification. |
| Watch `Pool Polluter` warning | Pool slots show 2-3 seconds of ghost Junk balls and striped capacity markers before Junk enters. | Warning duration 2-3 seconds. Active effect follows warning without ambiguity. | Player knows Pool is being polluted before the rhythm breaks. |
| Watch `Echo Breaker` warning | Break mark appears on Echo hot slot or Echo window before the next copy. The expected ghost hit collapses or weakens. | Warning duration 2-3 seconds or one clear pre-copy beat. | Player knows Echo was swallowed or weakened, not that damage randomly dropped. |
| Watch `Stagger Punisher` warning | Gap timer appears while squad charge-up is long. Punisher lands during the no-deployment gap. | Warning begins during visible charge gap. Active hit occurs before squad release. | Player knows the long charge gap was punished. |
| Answer post-battle questions | Result freezes, event strip appears, no answer key is shown. Player answers four questions plus confidence. | Answer flow begins within 5 seconds after battle end. | Player explains cause before being taught the correct answer. |

## 6. Acceptance Criteria

### Engineering Done (functional)

- [ ] MUST: Three battles run for 60-90 seconds each and reach the result screen.
- [ ] MUST: Each preset triggers its matching machine event, counter window, and axis-bound `Overdrive`.
- [ ] MUST: `Launch Flood` produces visible Pool rhythm and sustained frontline flow.
- [ ] MUST: `Tuning Echo` produces visible Echo copy behavior and repeated heavy-hit frontline changes.
- [ ] MUST: `Unit Queue Burst` produces visible queue buildup and grouped release.
- [ ] MUST: Each counter has warning, active, and effect states.
- [ ] MUST: Result screen records the four questions, four confidence values, observer notes, `correct_count_0_to_4`, `unit_only_bias_flag`, and `overdrive_panic_flag`.
- [ ] MUST: Build contains no shop, race expansion, relic, economy, node map, backend, networking, or old Web MVP dependency.
- [ ] SHOULD: Battle order can be randomized for target-player sessions.
- [ ] SHOULD: Event strip can be reviewed after each battle before answers are scored.

### Design Done (experiential)

- [ ] MUST: Among 3-5 target players, at least 3 players answer at least 3 of 4 questions correctly after each battle.
- [ ] MUST: At least 3/5 players can name a non-`Unit` axis as meaningful after seeing all three battles.
- [ ] MUST: At least 3/5 players can explain why `Launch` or `Tuning` changed the frontline without reducing the answer to "more units."
- [ ] MUST: At least 3/5 players can describe how one enemy counter disrupted a specific machine component: Pool, Echo slot/window, or charge gap.
- [ ] MUST: At least 3/5 players describe `Overdrive` as amplification of the current axis.
- [ ] MUST: No more than 2/5 players describe `Overdrive` mainly as rescue, shield, heal, clear-screen, or panic button.
- [ ] MUST: The soul is present: players can point to a machine event and then to the matching frontline change.
- [ ] SHOULD: In grayscale or low-color read, observer can still distinguish the three axes and three counter effects by shape, motion, and timing.

### NOT Done Until

- [ ] Someone other than the developer has played the build.
- [ ] At least 3 target players have completed the full three-battle blind answer flow.
- [ ] Observer has scored answers and marked both failure flags.
- [ ] If most answers are "more units" or "things got stronger", the build is not design-done even if it runs without errors.

## 7. Known Risks

| Risk | Impact | The Tempting Shortcut | Why It Kills the Experience |
|---|---|---|---|
| Missing causal trace | Critical | Make the frontline change by preset while the machine side only changes labels, colors, or numbers. | The player sees output but cannot explain `Launch / Tuning / Unit`. The test becomes noise. |
| Generic counter warning | High | Use the same red alert for all three counters. | Player only reads "enemy interference" and cannot name Pool pollution, Echo break, or charge-gap punishment. |
| Global `Overdrive` button | High | Put one big button near HP or bottom center, always pressable. | Player treats it as a panic tool. The diagnostic `Overdrive` test fails. |
| Unit feedback dominates | High | Make queue and unit arrivals louder than Launch and Tuning traces. | `Unit` becomes the only axis players trust. Primary risk is not tested honestly. |
| Result screen teaches before recording | High | Show answer labels or success explanations before questions are answered. | Test data becomes contaminated. Players repeat the UI instead of reporting what they read. |
| Color-only language | Medium | Use color as the only distinction between axes, counters, and states. | Grayscale and colorblind reads fail, and observers cannot tell whether shape/timing was readable. |
| Overbuilt content shell | Medium | Add shop, race, node map, meta, or polished menus because they feel product-like. | Extra systems hide the readability signal and waste prototype time. |

## 8. Test Hooks (how to verify)

| What to Test | How to Test | Pass Criteria |
|---|---|---|
| Battle flow | Run all three battles to completion. | Each battle reaches result screen, and each preset fires its matching counter and `Overdrive`. |
| 1-second combat read | During each battle, pause after an active axis moment and ask observer what changed. | Observer can identify active axis, counter state, and frontline signature without reading a preset title. |
| `Launch Flood` read | Watch Pool rhythm, return arrows, and frontline pressure. | Player or observer reads sustained flow, not one large hit or batch burst. |
| `Tuning Echo` read | Watch Echo hot slot, copy afterimage, and frontline impact. | Player or observer reads repeated hit, not faster spawning. |
| `Unit Queue Burst` read | Watch queue buildup, squad bracket, and release. | Player or observer reads charge then grouped push, not continuous flow. |
| Counter states | Trigger each counter once. | Warning appears on targeted component before active effect, and effect leaves a readable trace. |
| `Overdrive` direction | Fire each `Overdrive` at the intended moment. | Feedback appears on affected axis lane only. Event strip marks the amplified axis. |
| Blind answer flow | Run 3-5 target players through all three battles. | At least 3/5 meet the Design Done criteria in Section 6. |
| Failure flags | Review answers after test. | `unit_only_bias_flag` and `overdrive_panic_flag` are marked when wording shows those failure modes. |
| Scope discipline | Inspect build content. | No shop, race expansion, relic, economy, node map, backend, networking, or old Web MVP dependency exists. |
