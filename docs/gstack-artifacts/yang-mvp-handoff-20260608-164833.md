## 1. Build Target

Build a playable 15-20 minute complete short-run MVP v0 for PlanB.

The build must test whether a player can read this chain:

> three-warehouse physical ball machine -> unit queue -> direct `Deploy Lane` choice -> three-lane auto battle -> reward/shop response -> counter pressure -> Endpoint result.

This is not a vertical slice, not a Steam demo, not an art-production target, and not a standalone prototype slice. It is a complete short session with enough real systems to test readability.

## 2. Hypothesis

Hypothesis:

> 三仓球机 + 三路自动战斗 + Deploy Lane + 奖励/商店 + 反制 + Endpoint 能否形成可读短局。

The test fails if players can only explain the run as:

- "I made more units."
- "I clicked the right lane."
- "The enemies got harder."

The test passes only if players can point to `Launch / Tuning / Unit`, name at least one changed machine component, identify a counter target, and explain the Endpoint outcome through machine payoff or machine breakage.

## 3. The Soul

The soul of MVP v0 is machine-to-frontline readability.

If the player cannot watch one ball chain become a queue entry, see that entry land on a chosen lane, and later connect reward/shop/counter choices to the battle result, this is not PlanB. It is just an auto-battler with a noisy machine beside it.

The one thing that cannot be wrong:

> Active machine events must create visible battlefield consequences, not hidden math.

## 7. Gameplay Requirements

| Player Action | Expected Response | Timing | Feel Target |
|---|---|---|---|

| Read result page | Player sees main axis, key choices, counter target, Deploy Lane impact, Endpoint payoff/break reason, and next watch tag on failure. | Immediately after win/loss. | The run teaches through facts, not resource compensation. |

## 10. Acceptance Criteria

### Engineering Done

- [ ] The build starts a new MVP v0 run without requiring archived code or deleted scripts.
- [ ] The run can be won or lost within the 15-20 minute target once tuned.
- [ ] Guardian selection happens before Battle 1 and persists for the run.
- [ ] The machine chain can produce queue entries from physical ball outcomes.
- [ ] Unit queue deploys to the current `Deploy Lane`.
- [ ] Three lanes resolve unit movement, combat, gates, base-circle attacks, and Guardian HP.
- [ ] Rewards, shop, Gold, rest, counters, Endpoint, and result page all exist in the session flow.
- [ ] Debug controls can force at least: Tuning result, Unit slot hit, counter family, reward/shop candidate, lane pressure, Endpoint state.
- [ ] No player-facing flow requires npm/package scripts from the old repo state.
- [ ] The build does not read or depend on `docs/archive/prototypes/`.

### Design Done

- [ ] Battle 1 30-second test: a new player can point to Pool, Tuning, Unit slots, queue, and current `Deploy Lane`, then explain how a ball became a unit.
- [ ] First reward test: after choosing `Pool Pocket`, `Prime Charge`, or `Slot Primer`, the player can name the axis and expected battlefield read.
- [ ] Prime consequence test: `Prime Charge` can produce a visible route-state change or key queue result within 4-6s of a Prime hit.
- [ ] Shop test: the player can explain one neutral purchase cap, current Gold, item role, and why rest competes with machine choices.
- [ ] Counter attribution test: the player can say whether a counter attacked Pool, Echo value, or queue gap.
- [ ] Deploy Lane boundary test: the player understands lane clicks change deployment location only, not machine output or existing unit behavior.
- [ ] Endpoint test: after win/loss, the player can explain whether the main machine axis paid off or broke.
- [ ] Result page test: failure gives `main_break_reason` and `next_run_watch_tag`, without refund, continue, or next-run resource compensation.
- [ ] One-second glance test: in grayscale, a viewer can distinguish current selected lane, highest danger lane, active ball, and countered machine component.
- [ ] Guardian and Unit soft guardrails can be recorded over 10-20 runs, but not treated as final balance.

### NOT Done Until

- [ ] Someone other than the developer has played at least one full run or partial run through Endpoint.
- [ ] The playtest includes at least the six checkpoint questions from `docs/mvp-learning-checkpoints.md`.
- [ ] The result page fields have real run data, not static mock text.
- [ ] The team can name which failures are readability failures, tuning failures, or scope failures.

## 11. Known Risks

| Risk | Impact | Tempting Shortcut | Why It Kills The Experience |
|---|---|---|---|
| Machine chain unreadable | Critical | Let the machine run as visual noise and only make battle clear. | Player cannot connect choices to outcomes. |
| `Deploy Lane` dominates | Critical | Make lane warning brightest and most useful, then let player follow warnings. | The game becomes route whack-a-mole. |
| Physical overload | High | Keep all three boards equally bright. | Active cause chain disappears under motion. |
| Counters feel random | High | Spawn effects without target-component warning. | Player reads counter as enemy stat scaling. |
| Rewards become generic buffs | High | Show "+value" without warehouse/component/operation. | Three axes collapse into "more units." |
| Guardian becomes fourth system | High | Let Guardian clean sustained leaks or define run by itself. | Ball machine stops being the main system. |
| Unit becomes always best | High | Let high-demand slots open or fire too early without cost. | `Launch` and `Tuning` lose independent value. |
| Result page becomes flavor | Medium | Show win/loss prose without machine facts. | Failure does not teach the next run. |
| Final balance gets frozen too early | High | Treat first-pass values as shipped balance. | Current numbers are duties and debug starts, not final proof. |
| Old prototype leaks in | Critical | Reuse old Web MVP or Battle Lab behavior because it exists. | It bypasses current canon and corrupts the build target. |

## 13. Design Decisions Engineering Must Not Guess

If implementation needs any of these, stop and ask or keep it behind debug tuning. Do not silently turn these into final rules.

- Engine choice and production architecture.
- Final art style, final font, final icon set, final material rendering.
- Final audio assets and mix.
- Exact physical pin layout, block density, and slot-width implementation method.
- Inter-board random landing range.
- Cannon swing range, speed, coverage, and feel.
- Ball physics parameters: gravity, bounciness, speed, same-screen ball count.
- Exact return-channel shapes for Split, Recycle, and Waste.
- Exact Exposure Gate interpolation between start and fully exposed times.
- Each Guardian, neutral modifier, and counter's final physical expression.
- Final battle wave counts, enemy quantities, spawn intervals, and total HP budgets.
- Final balance for Hive units, Guardians, rewards, shop prices, rest impact, and counters.
- Whether `docs/ball-machine-physical.md` becomes final canon.
- Any rule that would make Guardian stronger than a weak base defender plus soft axis lean.
- Any rule that changes `Deploy Lane` into auto-recommend, cooldown, pending route, or unit control.
- Any rule that creates a base `Overdrive` button.

## 15. Test Hooks

| What To Test | How To Test | Pass Criteria |
|---|---|---|
| Battle 1 chain | Force a clean ball through Tuning into Unit slot, then queue and deploy. | Player can explain the chain in one sentence. |
| `Deploy Lane` boundary | Click lanes before and after queue deploys. | Only future queue deployment changes. Existing units do not change. |

| Counter attribution | Trigger each counter with warning and effect. | Player names Pool, Echo, or queue gap as target. |

| Soft guardrails | After 10-20 runs, inspect Guardian choice/success and Unit key queue shares. | Treat as tuning signals, not final balance proof. |

## 16. Debug Parameters, Not Final Balance

The following values can be implemented as first-pass data and tuned during playtest, but cannot be treated as final balance:

- Hive unit HP, damage, attack interval, speed, range, projectile speed, splash radius, sweep width, max targets.
- Guardian tactical damage, cooldown, duration, slow, radius, target count.
- Guardian strategic trigger chance, pity count, Gate miss count.
- Forge interval, Launcher interval, Pool normal occupancy targets.
- Route Board target distribution `65 / 15 / 15 / 5`.
- Tuning target distribution `55 / 15 / 15 / 15`.
- Unit exposure interpolation between start and fully exposed times.
- Lane Gate HP, Guardian HP, Endpoint HP.
- Enemy HP, damage, attack intervals, speed, spawn counts, spawn timings.
- Counter warning duration, active duration, trigger count, cooldown, Junk count, Stagger gap threshold.
- Battle duration targets and first-play failure targets.
- Gold/rest balance, reward/shop strength, price-band effectiveness.
- Physical ball gravity, bounce, speed, board layout, cannon swing, same-screen ball count.
- Final color values, contrast, iconography, material style, sound assets, and mix.

The first build should make these visible and easy to change. It should not bury them in code as if they are final.
