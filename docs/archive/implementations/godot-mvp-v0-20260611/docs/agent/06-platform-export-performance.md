# 06 — 平台、导出与性能规则（桌面 + Web 兼顾）

> 平台目标：MVP v0 同时兼顾桌面（Windows / macOS）和 Web（浏览器），以 **Compatibility 渲染器为基线**。先保证两端都稳定可玩，再谈画质。

## 1. 平台基线

- 使用 GDScript，不使用 C#（Godot 4 的 C# 当前无法导出 Web）。
- 渲染器统一用 **Compatibility**：它桌面和 Web 都能跑，避免出现“桌面 Forward+ 能跑、Web 跑不了”的分裂。
- Web 优先单线程导出，兼容性更好；多线程导出需要 cross-origin isolation 的服务器 header，MVP 不默认依赖。
- 目标浏览器优先 Chrome / Edge / Firefox；Safari 不作为第一优先验证浏览器。
- 桌面优先 Windows / macOS。

如果后续需要桌面专属高画质，再单独评估是否给桌面加 Forward+ 配置；当前默认不分裂渲染管线。

---

## 2. Web 导出限制（必须记住）

- Godot 4 Web 只能用 Compatibility 渲染方法；Forward+ / Mobile 渲染器不适用于 Web。
- Web 依赖浏览器 WebAssembly + WebGL 2.0。
- 多线程 Web 导出需要特殊 header；单线程更稳妥。
- Web（尤其移动端浏览器）CPU/GPU 比桌面紧张，球机物理 + 三路同屏单位是主要压力点。
- 用 Compatibility 做基线开发，可以让大部分问题在桌面就暴露，再到浏览器验证。

---

## 3. 性能预算

MVP 阶段先设一个硬预算挡板，后续用 profiler 修正。

> 重要：下面这些数字**没有任何设计文档或 playtest 依据，纯属经验拍的临时起手值**。它们只用来在没有实测前防止对象无限堆积，**不是已确认预算**。真实上限必须等在桌面 + 浏览器上用 profiler 实测后再定，不要把这些数字当成结论引用或写进设计文档。

临时起手值（无依据，待实测替换）：

```text
同屏球（RigidBody2D）：先按 <= 30 试（物理对象最贵，优先压这个）
同屏单位 + 敌人（单路 × 三路合计）：先按 <= 60 试
同屏掉落/伤害数字等轻对象：先按 <= 80 试
同屏粒子发射器：先按 <= 20 试
单张纹理：尽量 <= 2048x2048
Web 首包：越小越好，不要一次塞入全部未来资产
```

如果超预算，按顺序降：

1. 同屏球 / 物理对象数（回收落仓的球、限制并发球数）
2. 同屏单位/敌人数
3. 粒子数量
4. 大纹理尺寸
5. 动画帧数
6. 每帧检测频率

物理对象（球）是 Web 最敏感的部分，球机产出节奏要和回收/清理配合，避免球无限堆积。

---

## 4. 每帧逻辑规则

禁止在 `_process()` / `_physics_process()` 中随意做：`load()`、大量 `instantiate()` / `queue_free()`、全场景 `find_child()`、大量 `get_nodes_in_group()`、大量字符串拼接、每帧创建大 Array/Dictionary、复杂路径搜索。

推荐：预加载常用 `PackedScene`、缓存节点引用、按路缓存单位列表（见 `05-gameplay-patterns.md` 第 6 节）、用 `Area2D` 事件替代全量距离扫描、用 Timer/累积时间做低频检测、必要时上对象池（球、单位、伤害数字）。

---

## 5. 渲染与 2D 表现

Compatibility + Web 目标下：

- 粒子少而明显。
- Shader 少用，必须有降级方案（Compatibility 下部分高级特性不可用）。
- 避免大量透明叠加（球机物理区可能有很多重叠半透明，注意）。
- 控制 `CanvasLayer` 和 `Control` 复杂度（球机面板 + Deploy + HUD 同屏）。
- 灰阶可读约束（来自 `docs/ball-machine-physical.md` 候选草案）：关键信息不能只靠颜色区分，灰阶下也要可读。

---

## 6. 音频规则

Web 导出对音频有额外限制。MVP 阶段：

- 音频反馈短小。
- 不依赖复杂音频效果链。
- 不把关键玩法反馈只放在声音里（要有视觉反馈兜底）。
- 浏览器中实测音频启动（首次交互才能播放）、延迟和循环。

---

## 7. 导出验证

导出相关任务至少说明：

```text
导出了哪些平台？（桌面 / Web）
导出 preset 名称是什么？
是否在目标平台运行/在浏览器打开？
测试浏览器/系统是什么？
是否查看浏览器控制台？
是否有 WebGL / WASM / 音频报错？
桌面和 Web 表现是否一致？
```

推荐导出目录（不提交导出产物，除非明确要求发布构建）：

```text
build/desktop/
build/web/
```

---

## 8. 平台差异处理

如果桌面和 Web 需要不同配置，用 feature tags 或项目设置区分，常见策略：

- Web 降低同屏球/单位上限。
- Web 降低粒子数量。
- Web 用更小音频资源。
- Web 禁用昂贵特效。

差异配置要集中、可读，不要散落在各脚本里写 `if OS.has_feature("web")`。

---

## 9. 何时做底层优化

优先用 Node/Scene/RigidBody2D。只有 profiler 证明物理或 Node 成为瓶颈时，才考虑 `PhysicsServer2D` / `RenderingServer` 等底层 API，且需先确认。

底层 Server API 规则：只用于大量同类对象或明确瓶颈；必须保留资源引用避免 RID 对应资源被释放；不要每帧向 server 查询返回值；必须写清为什么普通 Node 不够用。

---

## 10. 性能问题处理顺序

遇到卡顿时按顺序做：

1. 复现场景固定化（哪条路、多少球、第几波）。
2. 打开 Godot profiler / monitor。
3. 区分 CPU、GPU、脚本、物理、渲染、资源加载。
4. 找最大瓶颈（球机物理常是首要嫌疑）。
5. 做最小改动。
6. 桌面 + 浏览器各测一次。
7. 记录结果。

不要凭感觉重构。
